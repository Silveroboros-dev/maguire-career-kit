# Два offline-грейдера: реализация и запуск

Реализованы `candidate_fit` (кандидат → JD) и `preference_fit` (роль → ожидания
кандидата). Они проверяют структурированный ответ относительно заранее
подготовленного `gold`. Это первая исполняемая версия на правилах, без LLM judge,
API, сторонних библиотек или вероятности интервью. Python 3.9+.

Публичный интерфейс — чистая функция `graders.grade(packet)`. Код разделён на
[общие проверки](graders/shared.py), [candidate-fit](graders/candidate.py) и
[preference-fit](graders/preference.py). Передача данных и результатов через
обычные JSON-объекты позволяет позже подключить их к Maguire. Сейчас эта папка
остаётся вне `kit/` и не входит в устанавливаемый продукт.

## Вход и выход

Точные поля описаны в [контракте реализации](IMPLEMENTATION_CONTRACT.md).
`run_offline.project(input_data, gold, answer)` создаёт пакет с исходными
источниками, единицами эталона и одним ответом. Она исключает `case_id`,
`answer_id`, название семейства, каталог ошибок и авторские expected verdicts.
Внутренние ID источников нужны только для связей; их переименование не должно
менять решение. Весь список ответов и `annotations.json` грейдеру не передаются.

```python
from run_offline import project
from graders import grade

packet = project(input_data, gold, one_answer)
result = grade(packet)
```

У результата есть `verdict`, `assurance: rule_checks_only` и `findings` с
критерием, целью, JSON-путём, кодом правила и объяснением:

- `fail`: найдено материальное нарушение реализованного правила.
- `pass`: реализованные правила не нашли нарушения. Это более слабое утверждение,
  чем полный смысловой PASS, определённый в RUBRIC.md.
- `invalid`: пакет не соответствует контракту; это технически невалидная оценка,
  а не плохое качество совета. Неожиданное исключение отдельно записывается в
  `execution_error`.

Версия не выставляет общий балл, не усредняет нарушения и не ранжирует человека.
Найденные материальные нарушения маркируются `major`; калибровки `critical` пока
нет. Режим abstain не реализован: смысловые пробелы правил видны в пропусках
ошибок, а не замаскированы массовым воздержанием.

## Какие проверки действительно работают

| Область | Реализовано | Существенное ограничение |
| --- | --- | --- |
| Контракт | Типы и поля, уникальные источники, даты не позже снимка, ссылки gold, запрет метаданных | Нет проверки истинности самого gold |
| Покрытие и метки | Все material targets, дубли, запрещённые цели, allowed labels | Смысл row определяется эталоном, не извлекается из нового JD |
| Доказательства | Буквальная цитата, существующий источник, достаточный набор ID, отозванные факты / заменённые условия | Цитата из нужного источника может не подтверждать конкретную фразу |
| Candidate-fit | Нет опыта из одного JD; ограниченные шаблоны самостоятельного подтверждения, prototype → production, unknown → inability, выдуманной метрики в rationale | Неполное понимание отрицаний, атрибуции и свободного текста; метрики в conclusion отдельно не разбираются |
| Preference-fit | Ограниченные шаблоны выдуманного исключения/offer, запрета исключения, компенсации must-have зарплатой | Не вычисляет все пороги и исключения из прозы; корректность меток сверяет с gold |
| Действие | Allowed actions; ограниченные шаблоны гарантированного результата | Конкретность, необходимость и полезность next_step полностью не проверяются |

Правила для английских фикстур. Нельзя переносить их заявленную точность на
русский или произвольную прозу. `required_points` и `forbidden_inferences` не
сравниваются дословно: такая проверка ошибочно наказывала бы перефразирование.
Грейдер не выполняет содержащиеся в JD инструкции. Но корректность реакции
ответа на произвольную prompt injection семантически не доказана.

## Воспроизведение

Из корня `maguire-career-kit`:

```sh
python3 -B -m unittest discover -s evals/career-quality-v1/tests -v
python3 -B evals/career-quality-v1/validate_dataset.py \
  --manifest evals/career-quality-v1/MANIFEST.json

# Новая папка обязательна: существующий прогон не перезаписывается.
python3 -B evals/career-quality-v1/run_offline.py \
  --run-dir evals/career-quality-v1/runs/baseline-v1

# Проверка уже сохранённого прогона без повторной оценки ответов.
python3 -B evals/career-quality-v1/run_offline.py \
  --run-dir evals/career-quality-v1/runs/baseline-v1 --verify
```

Для повторного запуска выберите новое имя, например `runs/reproduction-v1`.
Чтобы проверить свой заранее спроецированный JSONL, используйте
`grade_packets.py --packets /absolute/packets.jsonl --predictions /absolute/new.jsonl`.
Каждая входная строка содержит `packet` и `packet_sha256`: SHA-256 от UTF-8 JSON с
`sort_keys=True`, `ensure_ascii=False`, `separators=(',', ':')`.

## Как устроен прогон

1. Проверяются исходные 96 JSON-файлов по прежнему MANIFEST. До оценки ответов
   сохраняется `freeze.json` с хешами кода, тестов, рубрики, контракта и review.
2. 96 ответов превращаются в отдельные пакеты. Их содержимое задаёт SHA-256
   идентичность, порядок перемешивается фиксированным seed. Исходные ID находятся
   только в отдельном `mapping.json`.
3. Отдельный Python-процесс получает только `packets.jsonl`. На время каждого
   вызова `grade` Python audit hook запрещает файловый I/O, socket/process/os
   операции. Это защита от случайных вызовов, не adversarial OS sandbox.
4. Сохраняется и синхронизируется `predictions.jsonl`. Только после завершения
   процесса evaluator десериализует аннотации и выполняет сопоставление.
5. `measurement.json` содержит каждую оценку, пропуск, ложный отказ, invalid и
   точное совпадение критерия/цели. `RESULTS.md` — читаемый отчёт. `receipt.json`
   связывает артефакты и проверяет неизменность кода, исходных данных и Git HEAD.

Доли ложных решений имеют явно названные знаменатели: валидно оценённые ответы
и все попытки. Invalid остаются отдельной строкой и не улучшают незаметно
показатели. Отклонённый плохой ответ и правильно локализованный дефект — разные
показатели. Совпадение имён критериев тоже не доказывает смысловую точность.

Это development-проверка. Root и авторы уже видели этот набор; автор runtime не
открывал ответы/аннотации до прогона. Reviewer не просматривал их содержимое,
но общий структурный test runner десериализовал эти файлы. Поэтому нет заявления
о независимом слепом тесте. Локальные хеши не являются внешней подписью.

## Следующая интеграция

Для подключения к реальному потоку нужен адаптер `fit-brief.v1` → этот контракт,
подготовка и review gold для конкретной задачи, а затем проверка на новых ответах.
Отсутствие gold нельзя заменить автогенерированной разметкой и назвать проверенной
истиной. До отдельной валидации semantic judge и проверки человеком этот baseline
подходит для регрессий формата и некоторых смысловых ошибок, но не для
автоматического одобрения карьерного совета или прогноза интервью.
